# Feature 16.1: Always-Acknowledge Replies + Raw Reply Persistence into Synchronize Context

## Overview

Observed live: KOINCODE posted a review comment suggesting `colors.selectionFg`. The user replied correcting it — `colors.selection` already covers this, `selectionFg` doesn't exist. The reply went through the `process-comment-reply` pipeline (Feature 7), but the LLM's rule-extraction step judged the reply as not teaching a rule and returned `null`. Per the original spec, that meant: no GitHub reply, no memory stored — the correction vanished. On the next push, the `synchronize`-triggered re-review (Feature 16) repeated the exact same wrong suggestion across multiple comments.

## Root Causes

1. **Silent null.** `extractRule`'s prompt (`lib/ai/memory.ts`) was scoped to *conventions/preferences* ("we always use X over Y"). The user's reply was a **factual correction** ("X doesn't exist"), a shape the prompt didn't recognize as rule-worthy — so the LLM's `null` was arguably correct given its instructions, but the pipeline treated `null` as "nothing happened," posting no acknowledgment at all.
2. **Statelessness beyond repo_memories.** Even when extraction succeeds, `repo_memories` rows are generalized, repo-wide rules — disconnected from "on this specific comment thread, in this PR, the user already said X." Feature 16's "Previous Review" section (`lib/ai/prompts.ts`) only ever carried a review's `summary` and `comments` (with `pending`/`adopted` status) — never the raw reply text a user attached to a specific comment. So a correction that failed extraction (or one the LLM judged too narrow to generalize) had no path back into the next review's prompt at all.

## Fix

### 1. Always acknowledge

`processCommentReply` (`lib/inngest/functions.ts`) now posts a fixed `"okay 👍"` reply whenever `extractRule` returns `null`, instead of silently returning `{status: "skipped"}`. No extra classification step (e.g. distinguishing "thanks" from a substantive-but-unextracted reply) — the model's judgment call is already spent by the time `extractRule` returns; adding a second LLM-driven judgment just to decide whether to ack would reintroduce the same failure mode one level up. A flat acknowledgment is cheap and unambiguous.

### 2. Persist the raw reply onto the comment it replied to, unconditionally

The webhook handler (`app/api/webhooks/github/route.ts`) already resolves which `reviewId` + `githubCommentId` a reply is attached to (`handleReviewComment`) — it just wasn't forwarding `reviewId`/`parentCommentId` in the `comment/reply-received` event payload. Now it does.

`processCommentReply` gained a `persist-user-reply` step that runs **before** the LLM config check and rule extraction — it writes the raw `userReply` text onto the matching entry in that review's `comments` JSONB (new optional `userReply?: string` field on `ReviewComment`, `lib/db/schema/reviews.ts`), regardless of whether a rule is later extracted, deduplicated, or stored. This is the safety net: even when extraction misjudges a correction as non-rule-worthy, the raw correction still lands back on the exact comment for the next synchronize pass. It also runs even when there's no API key configured (moved ahead of the `!config` bailout) since it costs nothing beyond a DB read/write.

Feature 16's `previousReview.comments` (`lib/ai/review.ts`, `lib/ai/prompts.ts`) gained the same optional `userReply` field, threaded through from the DB in `processReview`'s `run-review` step. `buildReviewPrompt()`'s "Previous Review" section renders it under each comment as `Developer's reply: "..."` when present, with an added instruction: a comment carrying a developer's reply is authoritative — never restate the corrected claim or re-suggest the same fix under a different framing.

### 3. Broadened the extraction prompt (quality improvement, not the safety net)

`EXTRACT_RULE_SYSTEM_PROMPT` (`lib/ai/memory.ts`) now explicitly names factual corrections ("X doesn't exist", "Y already handles this") as rule-worthy alongside stated conventions, so corrections like the one that started this all have a real chance of becoming a durable, repo-wide `repo_memories` row — not just PR-scoped context. This is additive to fix #2, not a replacement: even a well-tuned prompt will occasionally misjudge a reply, so the raw-reply persistence is what actually closes the loop.

## Files Modified

| File | Change |
|------|--------|
| `app/api/webhooks/github/route.ts` | `comment/reply-received` event payload gains `reviewId` (already resolved in `handleReviewComment`, just wasn't forwarded) and `parentCommentId`. |
| `lib/inngest/functions.ts` | `processCommentReply` gains a `persist-user-reply` step (runs before the config/LLM steps, writes raw reply onto the matching `reviews.comments` entry unconditionally) and an `acknowledge-reply` step (posts `"okay 👍"` when `extractRule` returns null instead of returning silently). `processReview`'s `run-review` step threads `userReply` through into `previousReview.comments`. |

| `lib/ai/memory.ts` | `EXTRACT_RULE_SYSTEM_PROMPT` broadened to recognize factual corrections about the codebase, not just stated conventions/preferences, as rule-worthy. |

## Key Decisions

- **Fixed ack text, no LLM classification.** Considered having the model distinguish purely social replies ("thanks", "lgtm") from substantive-but-unextracted ones, only acking the latter. Rejected — the model's one judgment call already happened inside `extractRule`; a second one to decide *whether to ack* just moves the same misclassification risk to a new spot. A flat `"okay 👍"` costs nothing and removes the ambiguity entirely.
- **Raw-reply persistence is unconditional, not gated on extraction outcome.** This is deliberately the safety net under the extraction prompt, not something that only kicks in when extraction is "good enough." Even a perfectly tuned extraction prompt will misjudge some replies; the goal is for the next `synchronize` review to see the user's actual words regardless of what `extractRule` decided.
- **No new table.** The reply is attached directly to the existing `reviews.comments` JSONB entry it replied to (via `githubCommentId`), reusing the same join key `handleReviewComment` already computes for the webhook match. Avoids introducing a parallel `comment_replies` table that would need its own lookup/join at prompt-build time.
- **Extraction prompt broadening is additive, not the primary fix.** Worth doing since the original bug's correction ("there is no `selectionFg`") is exactly the kind of durable, repo-wide fact `repo_memories` should hold — but it doesn't replace the raw-reply persistence, since prompt quality can't guarantee zero misclassifications.
